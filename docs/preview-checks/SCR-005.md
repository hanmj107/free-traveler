   상태까지 확인 가능)
4. **Member(로그인):** "이용 가능한 기능" Chip 3개 + 로그아웃 버튼이 보이는지,
   로그아웃 클릭 시 Loading("로그아웃 중...") 후 Guest 화면으로 돌아가는지

   닉네임·연령대·스타일 수정 후 저장 시 "저장되었습니다" 문구가 보이는지
6. 내 활동 탭: 내가 쓴 동행글(제목 수정+모집 마감), 보낸 요청 상태, 받은 요청
   승인/거절, 차단 목록(해제), "새 동행글 작성하기" CTA가 각 항목이 0건일 때

   계정·비로그인 상태에서는 탭 자체가 렌더링되지 않는지)
8. 관리자 탭: 신고 목록 상태 변경(접수/검토중/처리완료) 시 성공/실패 안내 문구가
   보이는지, 항공·숙소 외부 URL 저장 시 형식이 올바르지 않은 값(예: `not a url`)을
   넣으면 저장 전에 오류 문구가 보이는지, 저장 성공/실패 안내가 보이는지
9. Mobile 뷰에서 탭·Section 구분이 자연스러운지, 큰 빈 영역이나 Placeholder
   문구가 없는지

## 참고

- 이 화면은 `TASKS/WAVE_PLAN.md`의 정식 순서(W16 Component → W17 Page
  Owner)보다 앞서 사용자 요청에 따라 구현되었다 — `TASKS/WAVE_STATE.json`에는
  실제 Task ID 기준으로 진행 상태가 반영되어 있다.
- "내 활동" 탭의 모집글 수정(제목)·모집 마감은 API-MATE-POSTS의 기존 파일
  (`src/app/api/mates/[id]/route.ts`)에 `PATCH` Handler를 추가해 구현했다
  (`mate_posts_update_own` RLS가 본인 글만 허용). 이 Task의 Expected Files
  범위 안에 있는 파일이라 별도 Task 없이 확장했다 — SCR-004에서 `GET /api/mates`
  필터를 조정했던 것과 같은 근거다.
- "받은 참가 요청" 목록에는 신청자의 닉네임을 표시하지 않는다. `profiles` 테이블의
  RLS(`profiles_select_own`)가 본인 행만 조회를 허용하도록 설계돼 있어, 다른
  사용자의 닉네임을 클라이언트에서 직접 조회할 수 없기 때문이다(의도된 개인정보
  보호 제약). 신청 메시지 내용으로 식별하도록 안내한다.
- `/travel-tools?tab=mate` 링크(내 활동의 "새 동행글 작성하기" CTA, SCR-004의
  Intro CTA와 동일)는 `travel-tools/page.tsx`가 아직 `tab` 쿼리 파라미터를 읽지
  않아 실제로는 기본 탭(항공)으로 열린다 — 이 화면(SCR-005)의 Expected Files
  밖이라 여기서 고치지 않았다. 필요하면 별도로 확인해 달라.
- 관리자 UI 접근은 Page가 `profiles.role`을 조회해 관리자 탭 렌더링 여부를
  결정하는 1차 방어선(`isAdminRole`)과, `reports`/`app_settings` RLS Policy가
  서버에서 다시 막는 2차 방어선 둘 다로 보호한다. 비관리자가 `PATCH
  /api/reports/[id]`나 `PUT /api/admin/external-urls`를 직접 호출해도 RLS가
  403으로 거부한다(Mock 기반 Unit Test로는 검증, 실제 Supabase 프로젝트로는
  아직 확인 못함).
- 실제 Supabase 인증 상태를 포함한 전체 흐름(회원가입 → 로그인 → 프로필 수정 →
  내 활동 → 관리자 신고 처리)은 마이그레이션이 아직 반영되지 않아 로컬에서 실제
  DB로 확인하지 못했다. Auth 상태 전이/관리자 Guard/URL 형식 검증 로직은
  `tests/unit/accountGuards.spec.ts`로 검증했고, 실제 Supabase 연결 후 다시
  확인한다.
